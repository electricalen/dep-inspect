# Releasing dep-inspect

This repository uses an explicit release PR model for npm publication.

The goal is to make every published npm version traceable back to:

- a reviewed pull request on GitHub
- a Git tag and GitHub Release for the same version
- an npm provenance attestation tied to the GitHub Actions workflow that produced the package

## Why This Setup

This release flow follows the same broad pattern used by many well-known open source npm projects:

- release intent is captured in committed changesets before release
- changelogs are generated from those release notes instead of handwritten after the fact
- publishing happens from CI, not from a maintainer laptop
- Git tags and GitHub Releases are created as part of the automated release flow
- npm trusted publishing is used so public releases can carry provenance attestations

That combination gives users a clean chain from `npm install` back to the tagged source in GitHub.

## Release Artifacts

For each published version, maintainers should expect all of the following to exist:

1. A merged release PR generated by Changesets.
2. A matching `package.json` version on `main`.
3. A matching Git tag for that version.
4. A matching GitHub Release.
5. A published npm package for that same version.
6. npm provenance attached to the published package when the package is public and the repository is public.

## Normal Development Flow

For any user-facing change:

```bash
pnpm changeset
```

Choose the correct SemVer bump:

- `patch` for backward-compatible fixes
- `minor` for backward-compatible features
- `major` for breaking changes

Write the summary as release-note text. Changesets will reuse it in `CHANGELOG.md` and in the GitHub Release.

For internal-only work such as docs-only changes, local tooling, or CI-only changes, a changeset is usually not required.

## What Happens Automatically

The release workflow is defined in [release.yml](./.github/workflows/release.yml).

When a pull request with unreleased changesets lands on `main`:

1. GitHub Actions runs the release workflow.
2. `changesets/action` opens or updates a release PR.
3. That PR bumps `package.json`, updates `CHANGELOG.md`, and removes consumed changesets.
4. Nothing is published yet; the release remains reviewable.

When the release PR is merged:

1. GitHub Actions runs again on `main`.
2. `changesets/action` publishes the package to npm.
3. A Git tag and GitHub Release are created for the published version.
4. Because publishing uses GitHub Actions OIDC with npm trusted publishing, npm can attach provenance to the release.

## Trusted Publishing And Provenance

This repository is configured to publish from GitHub Actions rather than a maintainer workstation.

The release workflow includes the pieces npm requires for trusted publishing and provenance:

- `id-token: write`
- a GitHub-hosted runner
- a public repository and public package
- explicit provenance configuration via `NPM_CONFIG_PROVENANCE=true`
- package-level provenance configuration in `package.json`

The workflow also uses `commitMode: github-api`, which means release commits and tags created by the action are attributed through GitHub's API and are signed by GitHub. That is separate from npm provenance, but it improves traceability on the GitHub side.

## Maintainer Checklist

Before merging a release PR:

1. Confirm the version bump matches the changesets included.
2. Review the generated `CHANGELOG.md` entries for clarity.
3. Confirm CI is green.
4. Confirm the package metadata still points to the canonical repository URL in `package.json`.

After merge:

1. Confirm the Git tag exists in GitHub.
2. Confirm the GitHub Release exists for the same version.
3. Confirm the npm version exists and shows provenance.
4. Confirm the published version number matches the tag and GitHub Release.

## User Verification

Users who want confidence that the npm package matches the GitHub release should be able to verify the chain in a few ways.

On npm:

- check that the published version has provenance information
- confirm npm links the package back to this repository and source commit

On GitHub:

- check that the version tag exists
- check that the tag and GitHub Release point to the same version
- review the tagged source and generated changelog entry

Locally after install:

```bash
npm audit signatures
```

That verifies registry signatures and available provenance attestations for installed packages.

## Notes On Changelogs

This repository uses Changesets as the changelog source of truth.

That is a common professional pattern in npm projects because it:

- records release intent in the same pull request as the code change
- avoids reconstructing release notes from raw commit history later
- generates deterministic version bumps and changelog entries
- keeps release PRs reviewable before publication
